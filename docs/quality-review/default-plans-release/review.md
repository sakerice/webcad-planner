### バルコニーの出隅はアプリ側を直した

受領版では、バルコニーの手すり壁1090の両端を60mm外へ出して角の欠けを埋めて
あった。これはアプリ側の挙動に対する手当てなので、**アプリを直して壁は芯へ
戻した**(x1=0 / x2=3640)。3階建ての指摘は8件→6件になった。

出隅の延長処理が `buildWall3D` の通常壁の枝にしか入っておらず、フェンスと格子は
芯線の端で止まっていた。壁には厚みがあるので、直交する2枚を芯で突き合わせると
外側の角に「厚/2 × 厚/2」の欠けが残る。編集中のスナップ
(`snapWallPointToAxes`)は芯どうしを合わせるところまでしかしないので、
角を埋めるのは描画側の仕事。実測:

| | 前面フェンスの外面 | 側面フェンスの外面 |
| --- | --- | --- |
| 直す前・壁を芯で止める | x = 0 | x = −60（60mmの欠け） |
| 直す前・壁を両端60mm延長 | x = −60 | x = −60（ぴったり） |
| **直した後・壁を芯で止める** | **x = −60** | **x = −60（ぴったり）** |

手で伸ばした場合と、アプリを直した場合の仕上がりは完全に一致する。違うのは、
アプリ側を直せば**フェンスを引いた全てのプラン**で角が閉じることと、プランに
回避策が残らないこと。`addBalconyFencePiece` と `addLatticePiece` の両方に入れた。

## 配置検査の当て方

既定間取りは「こういうものが作れる」と気づいてもらうためのたたき台で、今後も
改善が続く。そこで検査は**スナップショットではなく上限**にした
(`test_default_plans_bring_in_no_new_kind_of_problem`)。

- 記録済みの指摘の**範囲内**であれば通る。家具が50mm動いても黙る
- **記録に無い種類**の指摘が出たら落ちる
- 指摘が減った・直った場合も通る。改善を邪魔しない

行を足すときはリリース記録に「なぜ配置のほうが正しく、検査のほうが合っていない
のか」を書く。消すときは直すだけでよい。

再生成の一致だけは別に押さえてある。生成スクリプトを走らせても出荷JSONと
同じものができる、という検査で、アプリ上の手直しが黙って消える事故を防ぐ。
間取りを改善する分にはこの検査は落ちない(書き出し→レビューパッチに記録、の
流れを踏めばよい)。

検証: Node 56件・lint自己検査・Python 16件すべて通過。配置検査は9件→2件。
生成スクリプトが出荷中の JSON を内容一致で再生成することを確認。
2階建てを平面図で確認し、建具が壁1013の芯に乗ってホール側へ開くこと、階段と
ホールの境界が y=3040 で通ること、IHとシンクが向き合うこと、洋室Aの折れ戸の前が
空いていることを実測した。3Dはシーングラフで、新しい間仕切り壁と折れ戸2枚が
正しい座標に建ち、外したワードローブが消えていることを確認した
（ブラウザの3D描画が環境側で止まっており、この回は画で確認できていない）。
3階建ては変更していない。
