# 既定プラン品質チーム — 体制とレビュー運用

目的: house-planner mobile の既定プランを「数億円の家づくりでこのサイトを
選ぶ理由になる」品質に引き上げ、維持する。

## 体制 (`.claude/agents/` に定義)

| 役割 | エージェント | 責務 |
|---|---|---|
| 全体統括 | hc-orchestrator | 最高の注文住宅ホームコンサルタント。ラウンド計画・採否・ロールバック判断 |
| 調査 | research-housing-design | 住宅総合デザイン(外観・構成)の定石とクオリティライン |
| 調査 | research-interior | インテリア(家具・スタイリング・生活感)の定石 |
| 調査 | research-floorplan | 間取り・動線・寸法の定石 |
| 調査 | research-color-material | 外装/内装のカラー・素材マネジメント |
| 実装 | plan-implementer | tools/make_default_plan_2f.py と plan JSON の実装 |
| 評価 | review-interior-design | インテリアデザイン審査(暮らしの説得力) |
| 評価 | review-space-design | 空間デザイン審査(3D目線での納まり・見えがかり) |
| 評価 | review-architecture | 住宅設計審査(寸法・動線・法規感覚・整合) |
| 素材 | asset-maker | テクスチャ/モデル生成(PIL・Blender) |
| アプリ改修 | app-brushup-worker / app-brushup-reviewer | index.html 側の描画品質改善と、その差分レビュー |

## ラウンド運用

1. **調査**: 調査エージェントがクオリティライン(=合格基準)を具体値で更新する。
   基準は docs/quality-bar.md に追記し、以後の評価はこの基準に照らす。
2. **実装**: plan-implementer が生成スクリプトを変更。コミット単位を小さく保つ。
3. **機械検査**: `python3 tools/lint_plan.py` 違反0が実装完了の必要条件。
4. **評価**: レビューエージェント3種が独立に審査し、指摘を
   「重大(ロールバック要求可) / 要修正 / 提案」で格付けする。
5. **判定**: オーケストレータが指摘を裁定。重大指摘が残るラウンドの変更は
   `git revert` / リセットでロールバックし、原因をルーブリックに追記する。
6. 重大0・要修正0 になるまで 2〜5 を周回する。

## 目視レビューの手順 (全レビュアー共通)

- devサーバ: `python3 tools/dev_server.py <port>` → `index.html` を開く
- 3Dカメラはコンソールから直接指定できる:
  `applyStashedCamera({pos:[x,y,z], target:[x,y,z]})` (単位m, x=plan x/1000,
  z=plan y/1000, y=高さ。1F目線は y≈1.95、2F目線は y≈4.85)
- モード切替(平面図/外観3D/内観3D)・階切替の直後はビュー初期化で
  カメラが上書きされるため、描画完了後にもう一度適用する
- 最低限の定点: 南正面(道路から)・東西北の各面・玄関前・LDK目線2方向・
  各居室目線・階段見上げ/見下ろし・敷地と道路の際・塀の足元

## これまでに検出した不良クラス (再発チェックリスト)

- 向きの規約違反: 階段の上り方向 / 廻り階段の抜け方向 / 外階段・スロープの
  高低 / 家具の正面(キャビネットの背面が通路を向く等)
- 建具: window-door の doorOpenState 未指定(開いた見た目になる) /
  サッシ色の不統一 / 窓上端の通り不揃い / 掘り込み小口の白見え
- 動線: ドア・折戸の開閉域や正面に家具 / 掃き出し窓の前1m / 通路幅不足
  (キッチン通路は1000mm以上) / どこからも入れない部屋(PS以外)
- 接地: 敷地サーフェス(-35mm)上のアイテムの浮き / 道路端の見切れ /
  電柱モデル付属の電線が敷地上空を横切る
- 代用の禁止: custom-block の箱でモデルの代用をしない(床仕上げ・門柱を除く)。
  カタログ(fmp 445点 + im0261 240点)から寸法・高さの合うモデルを選ぶ。
  高さ種別に注意(例: fmp-Table34 は h629 のローテーブルで机ではない)

## ロールバック規約

- ラウンドの変更は1コミットにまとめ、レビューで重大指摘が出たら
  そのコミットを revert して再実装する(部分手直しで濁さない)
- 生成物(assets/default_plan.json)は常に tools/make_default_plan_2f.py から
  再生成できる状態を保つ(JSONへの手パッチ禁止)

### 30〜32 を足した理由(向きと取り合いは目視では必ず落ちる)

`rot` は「正面が向く方角」で、付け間違えても平面図では気付けない。3Dを
その角度まで回して初めて分かるので、目視レビューは必ず取りこぼす。実際に
**壁を向いたデスクとモニタ・道路に背を向けた隣家・家の壁へ吹き付ける室外機**
を同時に見落とした。以後は機械で見る。

- **30 家具の裏表**: 正面の先400mm以内に壁があり、**かつ背面側の壁の方が
  遠い** ものを違反にする。距離だけで判定すると、910モジュールのトイレの
  手洗いのように「部屋が狭いだけ」の正しい配置まで挙がる。裏返しは
  「背を向けるべき壁に顔を向けている」状態なので、前後の距離を比べれば
  狭い部屋の正解だけを通せる。
  壁の探索は **建具の高さを考慮する**。窓と同じ平面位置にある壁掛けエアコン
  (FL+2050)は、窓(1200-2030)が抜けていても壁に付いている。
- **31 壁付け家具の浮き**: 背面から120mm以内に壁が無いものを違反にする。
  家具の置き間違いだけでなく **壁そのものの抜け** が見つかる。実際、書斎の
  東側(x6370, y3640-4550)に壁が1枚無く、そこに置いた飾り棚が開口の中に
  立っているのをこれで見つけた。
  天板の上に載っている物(洗面台の上のボウル、デスクの上のモニタ)は除外する。
- **32 壁の継ぎ目のずれ**: 端点が相手の壁の芯から1mm以上ずれていたら違反。
  3Dの壁は芯から厚みの半分ずつ振った箱なので、端点が芯に乗ってさえいれば
  箱同士は必ず重なる。逆に数十mmずれると交差部に段差やスリットが出る。
  どの壁にも接していない自由端(L字の出隅など)は正しい場合があるので通す。

### 判定の当たり方を直したところ (2026-08)

既定間取り(2階建て/3階建て)を組み直したときに、**設計を歪めないと通らない
検査** が3つ見つかった。どれも検査側の当たり方が現実と合っていなかった。

- **19 全室への通行連続性 — 境界のセルを塞いでいた**
  障害物を有効幅の半分(300mm)だけ膨らませて格子を塞いでいたが、
  **ちょうど300mm離れた格子点まで塞いでいた**。その点を中心にすれば有効幅
  ちょうどの通路が取れるので通れるはずで、実寸645mmのベッド脇が
  「通れない」と判定されていた。切り上げ/切り捨てを1セルずらして直した。
  格子の刻みは100mmなので、この1セルが最大100mm分の誤判定になる。
- **26 収納家具の正面クリアランス — 押入れの中まで見ていた**
  短辺1200mm以下の収納室(押入・リネン庫・910幅のWIC)は、中に立ち入らず
  戸口の前に立って使う。中の棚に正面600mmを求めると、棚を置くこと自体が
  できなくなる。収納室の中は対象外にした。
- **37 居室の窓の数 — 部屋名ごとに矩形を束ねていた**
  そのため (a)壁で仕切られていないLDKとリビングが別勘定になり、
  (b)吹き抜けの上階に開けた高窓が「階が違う」ので数に入らなかった。
  どちらも「その部屋に光が届くか」という目的から外れている。
  **壁がその辺を6割以上覆っていない隣室は同じ空間**として数え、
  吹き抜けの部屋は上階の窓も自分の窓として数えるようにした。

同じ理由で `tools/audit_quality.py` の「代用ジオメトリ」判定も直した。
手書きの型リストが古くなっていて、実際にはGLBを読む自転車・洗濯機や、
専用の手続きジオメトリを持つ室外機・樹木・道路・電柱まで
「立方体で済ませている」と数えていた。**存在しない粗を報告する監査は、
見落とす監査と同じくらい害がある**ので、index.html の3D分岐を読んで
判定する(専用の組み立て関数かGLBを呼んでいるか)。

### 検査の判定基準で意図的に緩めているところ

- **13 前面通行帯**: 開口いっぱいが空いている必要はなく、幅600mmの通り道が
  連続して残っていれば通す。全面開口のキッチンでペニンシュラが一部を
  塞ぐ形を不良にしないため。
- **27 開閉窓の室内側**: 窓の開口高さと上下で干渉しないもの(腰窓下の机・
  欄間上のエアコン)と、上端1400mm以下で手を伸ばして越えられるものは対象外。
- **10 部屋への到達性**: 建具が無くても、境界に幅600mm以上の壁の切れ目が
  あって隣室に face していれば通す。ホールと廊下のように壁を切ってつなぐ
  形を「入れない」と誤検出していた。実際に通れるかは check19 が見る。

## 機械検査で拾えない、判断を残している事項

- **LDK上の梁**: 2階の壁 y3640(x2730-6370) と x3640(y3640-7280) は1階に壁が
  無く、3640mmのクリアスパンになる。天井2400・階高2700では梁成に使える
  のは約240mmで、実施設計では下がり天井かLDK内の柱が要る。
  check14 は「支持率0%かつ2730mm超」を止めるだけで、梁伏せは見ていない。
- **北側斜線**: 敷地の北の空きを1820とし、軒先(y-450)から境界まで1370で
  5m+1.25D = 6712 > 建物高さ6110 を満たす前提。東京の第一種高度地区
  (5m+0.6D)には届かないので、その地域なら北をさらに寄せる必要がある。
- **2階の居室バランス**: 洋室A 6.1帖 / 洋室B 4.6帖 で不均等。将来の不満に
  なるが、階段位置とトイレの奥行を優先して現状を採っている。
- **階段の吹き抜けが上階の床を抜く**: アプリは1階の階段アイテムの真上の
  2階の床を自動で抜く。上階でその範囲に部屋を置いても床は生えないので、
  階段の位置を動かしたら必ず 2階の平面図と3Dで床の有無を確かめること。
- **腰窓のカーテン**: カタログに腰窓丈(高さ1350)のカーテンが
  `curtain-230615` しか無く、これは襞の無い一枚板で3Dの見えがかりが弱い。
  襞のある `curtain-177647` は高さ2242で、天井2400・窓台660では床丈に
  なってしまい入らない。掃き出し窓は177647、腰窓は230615で使い分けている。
- **軒樋の竪樋の落とし先**: アプリが直下階の壁コーナーから自動で選ぶため、
  開口の上に落ちる場合がある。データ側から位置を指定する手段が無い。

## テクスチャの作り方 (tools/make_interior_textures.py)

テクスチャ1枚は **実世界の決まった寸法へ貼られる**。その寸法は index.html の
`TEX_TILE_M` にあり、画像はその寸法ちょうどの1タイルとして作る。
ここを間違えると板幅も目地も実寸からずれる。

| キー | フットプリント | 内訳 |
|---|---|---|
| wood_floor | 1818mm | 複合フローリングの定尺。2P(151.5mm)が12枚 |
| tile_floor | 1800mm | 600角タイル 3×3 |
| plaster / wall_int / plaster_white | 900mm | 塗り壁 |
| galvalume_dark | 900mm | 立平葺き 働き幅300mm × 3 |
| wood_cedar | 945mm | 杉本実羽目板 働き幅105mm × 9 |
| siding | 455mm | 窯業系サイディングの働き幅 |

守る数値(調査で裏を取ったもの):
- **床の彩度は C\* 12〜20**。実写のオークがこの範囲で、C\*35 はオレンジ色の
  プラスチックに見える。板間の明度差は ΔL\* 4〜8
- **木口(板の短辺の継ぎ目)を必ず入れる**。1行1本、隣の行とは300mm以上離す。
  木口が無いと床が壁紙に見える
- 木目は **幅方向のプロファイルを長手方向へ蛇行させて読む**。プロファイルを
  長手方向に作ると木目が板を横切る
- タイルの目地は **ΔL\* 5〜8**。今の主流は目地を目立たせない
- 塗り壁は **法線マップが本体**。アルベドの色ムラは ΔL\* 3 以下に抑え、
  凹凸はコテ波112mm / 中ムラ45mm / 肌12.5mm / 骨材(1mm=寒水3厘)の4スケール
- ガルバは金属として描く(roughness 0.42 / metalness 0.55)。塗装鋼板でも
  空のグラデーションが縦に映り込むのが見どころ

## 3Dモデルの作り方 (tools/blender/)

**曲面のあるものを手続き生成するときは、パーツを継ぎ足さない。** 継ぎ足すと
継ぎ目の始末に手数の大半を取られ、しかも必ずどこかで浮くか刺さる。
車のように面が連続している物は、実際のデザインと同じ順序で作る。

1. **三面図を数値で決める**(側面のトップライン/ベルトライン、平面の半幅、
   断面の形)。この3つの表がモデルの全てで、形を変えたいときはここだけ触る
2. 各ステーションで3つの図を引いて閉じた断面リングを作る
3. リングを橋渡しして **1枚の連続面** にする
4. キャラクターラインには **支持ループ** を寄せる。サブディビジョンは支持
   ループが無いと角を丸め切り、石鹸のような塊になる
5. ガラスのように **面全体を占める** 材質違いは、別メッシュにせず
   **同じ面のマテリアルを差し替える**。浮きようも刺さりようも無くなる
6. ランプのように **面の一部にしか無く形が決まっている** 物は、逆に
   マテリアルの差し替えでは表せない(下記)

### マテリアルの振り方 — ここで2度失敗した

- **1度目**: ガラスを別メッシュで重ねた → 継ぎ目に段差が出て、ガラスの
  真ん中に白い板が貫入した
- **2度目**: サブディビジョン後の面を **絶対座標の箱** で判定して振った →
  境界が面の格子を斜めに横切り、ヘッドランプの縁が階段状にギザついた。
  さらに箱どうしが重なって、テールランプの赤がサイドガラスに乗った
- **正解**: サブディビジョンを **かける前** の元の面に、格子の番号
  (ステーション i, リング j)で振る。境界が格子線そのものになるので原理的に
  ギザつかない。サブディビジョンは各面を4分割してマテリアルを引き継ぐため、
  分割後も境界は元の格子線に乗ったまま滑らかな曲線になる
- この方式の前提: **意匠の境目は必ずステーション線として置くこと**。
  ピラーの前後端・ガラスの端の y をステーション表に入れ忘れると、一番近い
  ステーションに丸められて意匠がずれる。`_check_feature_stations()` で落とす
- **帯(リング番号)で表せるのは車の側面だけ。** ヘッドランプが要るのは正面を
  向いた面で、ノーズが絞られている以上そこは前後の蓋にしかない。帯で振ると
  側面に細長い光る筋が出るだけで、正面から見ると消える。
  ランプは車体の平面輪郭 (x, y) の折れ線に沿わせた別形状として作り、
  法線方向へ8mm出す。**輪郭の半幅は 1.000 倍で拾うこと** —
  0.99倍などで内側に寄せると、サブディビジョンの縮みと合わさって車体に潜る
- **レンズは暗く。** 白いボディに淡い水色のレンズを置いても背景に溶けて、
  ランプが付いていないように見える。実車もレンズの中は暗く、光るのは中の
  リフレクタとデイライトの線だけ。この明暗差が顔付きを作る
- **ランプの z は、その y での車体の天端(TOP_LINE)より下に収める。**
  はみ出すと車体から赤い旗が立つ

### バウンディングボックスはカタログ値と一致させる

アプリの `makeGltfBoxFitClone` は **3軸を独立に伸縮する**。GLBのbboxが
カタログの `w×d×h` と比が違うと、その軸だけ潰れる(ドアミラーぶん幅が
1955mmあるのにカタログが1800だと、幅だけ8%細い車になる)。
車は「ボディ1690 + ミラーで1800ちょうど」に設計して合わせている。
`car2_build.py` は最後に bbox を測り、1%を超えるずれは黙って潰さず落とす。

## 2Dアイコン(平面図の記号とライブラリのサムネイル)

**モデルを追加/作り直したら必ず `tools/blender/make_icons.py` を通す。**

    Blender --background --factory-startup --python tools/blender/make_icons.py -- <glb>...

- 他のモデルのアイコンを流用すると、平面図に別物の記号が並ぶ
  (シーリングファンの位置に庭木が描かれる、という状態を実際に出した)
- GLBを作り直したときも撮り直しが要る。**GLBだけ新しくアイコンが古い**状態は
  ファイルの日付を見るまで誰も気付けない
- top は真上から。平面図は rot に従って画像を回すので、画像の上端が
  モデルの正面(+Y)でなければ向きが合わない
- thumb は正面(+Y)の左手前から。カメラを -Y 側に置くと背面しか写らず、
  表札もインターホンも無い真っ平らな面をサムネにしてしまう(実際にやった)
- 「正面が +Y」はモデル側の約束。ウッドデッキは幕板が3面にしか無いので、
  幕板側を +Y にして配置側を rot=180 にした(見た目は変わらない)

### Blender で繰り返し踏んだ罠

- **ブーリアンを適用すると、マテリアルを持たないカッター由来の空スロットが
  index 0 に残る。** そのまま append すると自分で振った material_index が
  1つずれる(ボディが空スロット、ガラスがボディ色になる)。
  `ob.data.materials.clear()` してから積むこと
- **Principled BSDF の Base Color はリニア。** sRGB の16進をそのまま入れると
  1段明るく彩度が抜けて出る。狙った茶色が薄いベージュになる。`hex_lin()` を通す
- **`render_glb.py` のカメラ。** モデルの正面は +Y、カメラは -Z を向くので、
  正面を見るには rot_z=180 側に置く。ここを間違えると背面だけを見て
  「正面が作れていない」と誤診する

### 見た目を決める数値(モデルでもテクスチャでも共通)

- 木の彩度は **C\* 12〜20**。超えるとプラスチックに見える
- 板を張った面には **必ず目地**(デッキ材なら3〜6mm)。目地の暗い線が無いと
  「板」に見えない
- 角は必ず面取りする(デッキ材1〜2mm)。角が立ったままだと樹脂の塊に見える

## 吹き抜けの作り方

**天井高を数値で書かないこと。** 階高・床スラブ・階数から決まる値なので、
手で計算すると階高を変えた瞬間に上階の天井と食い違い、スラブの小口が室内に
見える(最初の実装は 5280 と手で書いて 120mm 低かった)。

やることは3つ。

1. **抜きたい範囲の上階から部屋を消す。** 部屋の矩形が床を作るので、部屋が
   ある限り床は張られる
2. **真下の部屋に `ceiling: {"type":"void","toFloor": N}` を書く。**
   高さはアプリが `floorBaseY(N) + 階高(N) - floorBaseY(自階)` から計算する。
   2層以上抜くときは toFloor を上げるだけ
3. **縁に手すり壁を置く**(`wallStyle="balcony-fence"`)。壁で塞ぐと2層の抜けが
   死ぬ。置き忘れは check29 が止める

UIからは 部屋 → 天井 → 種類「吹き抜け」→ 抜き先の階、で同じことができる。
上階に部屋が残っている場合は選べず、理由が表示される。

### 部屋を割る必要がある

天井は部屋ごとの属性なので、**吹き抜けの範囲と部屋の矩形は一致していないと
いけない**。部屋の一部だけを抜きたいときは、その境界で部屋を2つに割る。
既定プランでは LDK を「LDK(天井2400)」と「リビング(吹き抜け)」に割っている。

## 内装のカラーバランス

明度を **天井 > 壁 > 建具 > 床 > 家具** の順に単調に下げ、**明るい面ほど彩度を
落とす**(壁・天井 C\*≤5 / 床 C\*13台 / 木部アクセント C\*20台)。この2つを
守っている限り色数を増やしても濁らない。アクセントは1室1面に集約する。

内装は **壁1枚ごとに `interiorColor` / `interiorTexture` を持たせる**。
`interiorWallSettings` の whole / floor を linked にすると解決順の関係で
全部の壁が同じ仕上げに固定され、アクセント壁を1枚も作れなくなる。

## 天井付けの器具 (高さの基準が3つあり、取り違えると浮く)

同じ「高さ」でも基準が3つある。ここを取り違えたのが、照明が全灯天井から
浮いていた原因(1階で308mm、2階で124mm)。

    部屋の天井高 roomCeilingHeightM … 床スラブ**下端**(floorBaseY)から
    アイテムの elev                 … 床**仕上げ面**(floorTopY)から
    天井面のメッシュ                 … 上の天井高から仕上げ厚 12mm ぶん下

取付高さは必ず **天井仕上げ面** に合わせる。式は1つで、3か所に同じものを置く。

    天井仕上げ面(elev基準) = 部屋の天井高 - その階の床スラブ - 12

    1階 2700-0-12   = 2688
    2階 2700-180-12 = 2508
    吹抜 5400-0-12  = 5388

  - `index.html` の `ceilingFinishElevationMm()` … 新規配置の既定値
  - `tools/make_default_plan_2f.py` の `ceiling_elev()` … 既定プランの生成
  - `tools/lint_plan.py` の `ceiling_finish_mm()` … 上2つの結果を突き合わせる

**照明の elev は「取付面(=天井仕上げ面)」の高さ**であって器具の中心ではない。
器具の形は種類ごとに違うので、ぶら下げ量は `build3DLightItem` が種類ごとに持つ
(シーリング/ライン/スポットは上面を天井へ、ダウンライトはトリムリングを天井面へ
置いてレンズだけ天井裏に残す)。elev を中心として扱うと、必ず半分めり込むか
半分浮く。

**モデル(GLB)の器具は底面が elev** なので、天井付けのモデルは
`elev = 天井仕上げ面 - モデル高` になる。シーリングファンはキャノピー上端が
モデルの上端になるよう作ってあるので、この式でキャノピーが天井に密着する。

内観3Dは間取りを見下ろすために天井を描かない(仕様)。器具が天井に付いている
ことを目で確かめるならウォークスルーを使う。

## 壁の出隅 (芯線の端を同じ点に置くだけでは角が閉じない)

壁は「芯線から厚/2」の箱として立つ。直交する2枚の芯線の端を同じ点に置くと、

    横壁の箱: x 0..len  / y -60..+60
    縦壁の箱: x -60..+60 / y 0..len

となり、**x -60..0 かつ y -60..0 の「厚/2 × 厚/2」がどちらにも入らない**。
出隅が四角く欠け、階段状に見える。データ側は正しいので lint では見つからない
(端点は相手の芯にちょうど乗っている)。描画側の問題。

`wallEndCornerExtensionMm(w, atEnd)` が端ごとの延長量を返す。守っている条件:

- **平行な継ぎ足しでは伸ばさない**(角ができない)
- **T字では伸ばさない**。そこは既に相手の箱で埋まっており、伸ばすと相手の
  反対側の面から自分の断面が顔を出す(外壁のファサードに内壁の色の帯が出る)
- 「相手も端で出会っているか」だけでは足りない。南外壁が x6370 で2枚に
  分かれている所へ背骨の壁が突き当たると、相手の1枚は端だが実際にはもう1枚が
  続いているので埋まっている。**伸ばす先を実際にサンプリングして、覆われて
  いないときだけ伸ばす**
- 覆っていると数えられるのは **solid かつ同じ高さまで立っている壁だけ**。
  2階南西の隅はバルコニーの手すり壁(高さ1100)が塞いでいるだけで、その上は
  開いていた。これはテストが見つけた

延長は **3D のコア・外装面・平面図・JIS図面の4か所すべてに同じ値** を使う。
内装仕上げ面だけは別に `wallCornerExtensionMm` が面同士を突き合わせている。
検査は `tools/tests/wall-corner.test.cjs`(node:vm で実際に走らせて数値で見る)。

## アプリ側で直した描画不良 (再発したら index.html を疑う)

- `o.sill||1.0`: 掃き出し窓(sill=0)が既定値に化け、窓下に1mの壁が立ち
  窓上の壁が消えていた。0 を falsy にする `||` は数値の既定値に使わない
- build3DTree が Math.random() と固定寸法で、離隔が守れず再現性も無かった
- バルコニー手すりが floorBaseY から立ち、スラブ厚ぶん低かった
- フラット屋根・片流れ庇に軒天(下面)が無かった
- custom-block が側面用マテリアルを天端にも貼り、テクスチャが伸びていた
- 引違いサッシの枠見込みが70mmで、室内側の掘り込み小口が露出していた
- 屋内階段に手すりが生成されていなかった
- 平天井が階高で丸められ、吹き抜けが作れなかった。上に階はあるのにその位置
  だけ部屋が無い場合に限り、階高を超えてよい(最上階の丸めは従来どおり)
- 天井を張る判定が直上階の屋根しか見ておらず、吹き抜けの上が抜けて見えた
- 幅木が存在しなかった。壁と床が幅ゼロのエッジで突き合わさっていた
- テクスチャの実寸フットプリントが床0.9m/壁0.45mの2定数しかなく、同じ画像が
  面によって2倍違う寸法で貼られていた
- 法線マップの受け口はあるのに、誰も渡していなかった
- 陸屋根の板を基準面の下にぶら下げており、壁の天面と屋根の天面が同じ
  高さで重なって、真上から見ると壁の割付がちらついていた。高さモデル
  (roofLocalVertices)は 0〜+thick で持っており、3D描画だけがずれていた
