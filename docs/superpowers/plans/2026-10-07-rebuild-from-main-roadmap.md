# 本番から作り直す実装計画（全体の地図）

> **For agentic workers:** この文書は全体の順序と範囲を決める地図。各段階に着手するとき、その段階だけの詳細計画（ファイル・テスト・手順まで）を
> `docs/superpowers/plans/` に別に書き、利用者の確認を取ってから実装する。

**Goal:** PR #76（Codex 製、PR #72〜#75 の統合版）で狙った5つの機能を、本番（main）から小さく作り直し、1段ずつ本番に出す。
今の利用者が作ってきたプランは、どの段階でも必ずそのまま開ける状態を保つ。

**作り直す理由:** PR #76 は新機能の途中で、保存・JSON読込・ウォークスルーの壁の当たり判定・建具の描画まで差し替えていた。
その結果、今の利用者の保存プランが開けなくなっていた。問題の一覧は `docs/pr76-review/findings.md`。

**PR #76 の扱い:** 参考として開いたまま残す。取り出して使うのは、洋館のモデル、洋館への差し替え対応表の考え方、既存の冷蔵庫・収納・シンクを調べた記録だけ。
ほかの直しは、1件ずつ main と比べて、良いものだけ取り込む。

---

## 全段階に共通の決まり

- **既存のプランが開けることが最優先。** 本番で作られた保存プランと JSON ファイルは、どの段階でも、今と同じ操作で同じ見た目に開けること。開けなくなる変更は出さない
- **1つの PR は1つの目的。** 本番に出すのは、利用者が触って完結する単位。完成していない機能は、URL に付ける隠しスイッチの裏に置いてから出す。利用者の画面には出さない
- **本番に出すときは毎回たずねる**（AGENTS.md）。出す前には次を確かめる
  - 既存のテストが全部通る
  - 0-1 で作る互換テストが通る（`sh tools/run_browser_tests.sh plan-compat`）
  - ブラウザで main と並べて、変えていないところが変わっていないこと
- **UI は DESIGN.md に従い、出す前に利用者のレビューを受ける。** 既にある導線（カタログのパネル等）を作り直さない
- **画面の言葉は利用者の言葉で書く。** 内部の用語・英語のコード・ハッシュ値を画面に出さない
- **3Dモデルは Blender で独自に制作する。**
  - 前面は +Z、上は +Y、原点は底面の中心
  - 素材ごとに色を変えられるよう、マテリアルを部位で分ける
  - .blend・GLB・正面と背面の検証画像をリポジトリに残す
- **Codex の担当は「部品の製作」。** モデルと、それに付く説明データ（後述の「セット定義」）を作る。index.html と、アプリの動きを決める JS には触らない。
  納品物は 1-4 で作る検査を通るものに限る

## 段階の一覧と順序（案）

| 順 | 段階 | 利用者にとって何が変わるか | 本番に出す回数（目安） |
|---|---|---|---|
| 0 | 土台づくり（互換テスト・性能の基準・再現度の測り方） | 画面は変わらない。以降の変更で既存プランが壊れたら、出す前に止まる | 1〜2 |
| 1 | アセットの切り替え（ゲームの舞台作り向け） | カタログで「標準／洋館」を切り替えて配置できる。置いた家具を一括で洋館に差し替えられる | 3〜4 |
| 2 | 複数の間取りの比較モード（同じ画面の中） | 画面を左右に分けて2つの間取りを並べ、どちらも編集・保存できる | 3〜4 |
| 3 | 間取り図からの下書きの再現度 | 読み取った下書きが元の図面に近くなる。測った数字で効果を示す | 測定の結果しだい |
| 4 | 動作の最適化と、その上での表現力向上 | iPad でも軽く動く。浮いた余力で見た目を上げる | 測定の結果しだい |
| 5 | 三人称視点のウォークスルー | 人物を後ろから見ながら家の中を歩ける | 2〜3（完成までは隠しスイッチの裏） |

**この順にする理由**
- 1 を最初に置くのは、モデルがほぼ揃っていて、既存の保存や描画に触らずに済み、一番安全に出せるから。
- 2 を次に置くのは、1 の差し替え結果を元のプランと並べて見たい、という使い道にも効くから。
- 4 を 5 より先に置くのは、三人称視点は描画の負荷を増やすので、先に余力を作っておきたいから。
- 3 は、0 で測り方が決まれば、ほかの段階と並行して進められる。ただし AI の利用回数を使うので、測る量は相談して決める。

## 段階0: 土台づくり

### 0-1. 既存プランの互換テスト
- **目的:** 以降のどの変更でも、今の本番の保存プランと JSON が同じように開けることを、本番に出す前に機械で確かめる。
- **作るもの**
  - 本番の「保存」で作られるデータと、「JSON」で書き出されるファイルの見本
    - 既定プラン2種
    - 古い形式の値を含むもの（壁の厚さが文字列、ゼロ長の壁、古い家具ID）
  - それぞれについて、テストで次を確かめる
    - 読み込んで、壁・部屋・家具・建具の数と主な寸法が変わらない
    - 起動時の「前回保存したプランがあります」から1回で開ける
    - 「読込」で JSON が開ける
- **完了の条件:** main で全部通ること。PR #76 の状態で流すと失敗すること（旧保存が開けない、を検出できること）。

### 0-2. 性能の基準
- **状況（2026-10-08）:** 測定の仕組み（`?bench=1`）と Mac の基準は `docs/perf/README.md`。iPad Pro での測定は、本番に出たあと利用者が URL を開いて行う。
  - 本番には既に AO（N8AO）と夜景だけの Bloom が入っている。操作中は解像度を下げ、この2つを止める仕組みもある。段階4はこの上に足す
- **目的:** 「軽くなった／重くなった」を数字で言えるようにする。
- **作るもの:** 既定プラン2種について、決まった視点・決まった操作（平面図、外観3D、内観3D、ウォークスルーで廊下を歩く）を流し、次を記録する手順と結果。
  - 1コマにかかる時間
  - 3D に入るまでの時間
  - メモリ
- 既存の `docs/quality-review/motion-render-benchmark.json` の形式を使えるなら、そちらに合わせる。
- **相談:** 狙う端末（iPad の機種）と、目標のコマ数。

### 0-3. 読み取り再現度の測り方
- **目的:** 段階3の効果を、見た目の印象ではなく数字で示す。
- **作るもの**
  - 正解付きの図面セット（図面と、人が直した正しいプランの組）
  - 読み取り結果と正解を比べて点数を出す道具
    - 壁の位置と長さの一致
    - 部屋の数・名前・面積の一致
    - 建具の数と位置の一致
- 最初の図面は手持ちの `tools/tests/fixtures/madori-3f.pdf` から始める。
- **相談:** 正解付きの図面を何枚用意できるか。1回測るごとの AI の利用回数の上限。

## 段階1: アセットの切り替え（ゲームの舞台作り向け）

将来「日本古民家」などのセットを足していくことを前提に、**セットを増やすときに、アプリ側のコードを触らなくて済む形**にする。

### 1-1. セットの仕組みと、カタログでの切り替え
- **状況（2026-10-08）:** 1-1・1-2・1-4 を1つの PR にまとめて実装。画面のレビュー待ち
- **セット定義**（1つの JSON）に次を持たせる。
  - セットの名前
  - モデルの一覧（名前・分類・寸法・色を変えられる部位）
  - 差し替え対応表（標準のどの家具を、このセットのどれに替えるか）
- **入口はカタログのパネルの先頭。** そこに「表示するセット」の選択（標準・洋館。複数を同時に選べる）を置き、今どのセットを表示中かが常に分かるようにする。
  - PR #76 では、検索カードの中のボタンから開くモーダルの奥にあった。これはやめる。
- 洋館のモデルは、普通の日本の住宅のプランにも1点ずつ置ける。
- 切り替えても、置いてある家具と間取りは変わらない。最初の状態は「標準だけを表示」とし、標準セットの見た目と動きは今と1点も変えない。
- **完了の条件:** 0-1 が通る。標準セットのカタログの中身と並び順が main と同じ。

### 1-2. 洋館セットを載せる
- PR #76 から次の2つを取り出す。
  - 55点の GLB
  - 次の3種類を外したセット定義
    - 住宅・ゲームのどちらでも扱いに迷う分類（「事件跡」「探索小物」）。残すかどうかは利用者が決める
    - 寸法が実物から外れているもの（ソファの高さ 1120mm など）
    - .blend が無いもの
- 正面の向きと上方向を、モデル1点ずつ確かめる。
- **権利の台帳**に「Codex が独自に制作」と記録する。.blend が無い47点も、その旨を書く。

### 1-3. 置いてある家具の一括差し替え
- **差し替えは、今のプランにそのまま適用する。** Undo 1回で元に戻せるようにする。
  - 保存は今の本番の「1つだけ保存」の仕組みに戻すので、「別のプランとして作る」はしない。
- 差し替える前に「n点を差し替え、m点はそのまま」と一覧で見せる。
  - ゲーム向けなので、対応表にある物は**最初から全部チェックを入れておく**。
  - PR #76 では、最初から差し替わるのが176点中3点だった。
- 差し替えたあとに3D表示へ切り替え、結果がすぐ見えるようにする。
- 段階2の比較モードができたら、「差し替え前と並べて見る」をここから開けるようにする。

### 1-4. セットを足すための手順書と検査（Codex 向け）
- **手順書:** `docs/asset-sets.md` に、新しいセット（例: 日本古民家）を作るときに納めるものを書く。
  - モデル
  - 検証画像
  - .blend
  - セット定義
  - 対応表
  - 台帳への記入
- **検査の道具:** 納品物を機械で検査する。
  - 正面と上方向
  - 原点
  - 寸法が定義と合っているか
  - 面数の上限
  - 色を変えられる部位があるか
  - 対応表が実在する ID を指しているか
- Codex の作業は「この検査が通るまで」を完了とする。

## 段階2: 複数の間取りの比較モード（同じ画面の中）

### 決まっていること
- 比較中は、今の画面の図面の部分が左右に分かれる。上のボタン類は1組だけ。
- **どちらの間取りも操作できる。** 押した側が「編集中」になり、ボタン・Undo・保存はその側に効く。
- 比較をやめると、元の1画面に戻る。
- 保存の仕組みは、今の本番のまま（ブラウザに1つ保存＋JSON の書き出し・読込）。

### 2-0. 技術の下見（本番には出さない）
- 今のアプリは、編集中の間取りを1つだけ持つ作りになっている。2つ目の間取りの持ち方を試作で確かめる。
  - 1つの編集機能の中で、2つの間取りの中身を入れ替えながら使う方法
  - 図面の描画だけを2面にする方法
- **最初は平面図での比較だけ。** 3D の左右比較は 2-4 に分ける。
- 結果は、詳細計画を書く前に利用者に報告する。

### 2-1. 平面図での左右比較
- **比較相手の選び方**
  - 「今のプランを複製」
  - 「JSON ファイルを開く」
  - 「ブラウザに保存したプラン」
- 左右の倍率と位置を揃える。揃えるかどうかは切り替えられる。
- 編集中の側に枠と名前を出し、どちらを触っているかが一目で分かるようにする。

### 2-2. 比較中の保存
- **左（もともと開いていたプラン）:** 今と同じ「保存」が効く。
- **右:** JSON ファイルとして書き出す。
- 比較をやめるときに右が未保存なら、書き出すか、捨てるかをたずねる。

### 2-3. プランに名前を持たせる（複数の間取りを扱いやすくする第一歩）
- プランに「名前」を持たせる。名前は JSON の中に入れる。
- 書き出すときのファイル名は「名前_日付.json」にする。
- 比較中は、左右それぞれに名前を出す。
- 古い JSON（名前が無い）は、今まで通り開ける。名前は空として扱う。

### 2-4. 3D での左右比較
- 内観3D・外観3D も左右に並べ、視点を同期できるようにする。
- 描画の負荷が2倍になるので、段階4の測定で問題が無いことを確かめてから出す。

### 2-5.（要相談）ブラウザに複数のプランを保存できる一覧
2-1〜2-3 を使ってみてから決める。作る場合の形は次の通り。
- 今の「1つだけ保存」は「前回のプラン」としてそのまま残す。旧保存は確認1回で開ける。
- 別に「名前を付けて保存」の一覧を足す。
  - 一覧の各行: 名前・保存日時・縮小画像
  - 名前の変更と削除ができる
- ブラウザの保存はブラウザを消すと失われる。そのため一覧から JSON への書き出しを1回でできるようにし、画面でも案内する。

## 段階3: 間取り図からの下書きの再現度

### 3-1. 今の本番の点数を測る
- 0-3 の道具で、今の本番の読み取りの点数を記録する。

### 3-2. 既にある改善案を、同じ道具で比べる
- 比べる候補
  - PR #76 の新しい読み取り方式
  - 開いたままの PR #69・#70・#71（寸法の根拠を残す、例示から特定図面の答えを外す、PDF の切り出しを確認する）
- 各候補を手元で動かし、同じ図面で点数を出す。
- **点数が上がったものだけを取り込む。** 取り込む単位は、1つの改善につき1つの PR。

### 3-3. 弾かれている部品を足す
- 読み取りでは認識されるのに、対応するモデルが無くて弾かれているものを、点数への影響が大きい順に Codex へ発注する。
  - 引違い戸・折れ戸・両開き扉・開閉する窓・階段・システムキッチンなど。一覧は findings.md の 6-1
- 発注するのはモデルと、開き方・段の高さなどの説明データ。取り込み側の対応は、こちらで実装する。

### 3-4. 確認画面の作り直し
- 読み取り結果を利用者が直す画面は、点数が上がった方式が決まってから作り直す。
- 方針
  - 専門的な確認は機械で済ませる
  - 利用者には「この壁は正しいか」の形でだけ聞く

## 段階4: 動作の最適化と、その上での表現力向上

- **4-3.** 浮いた余力の範囲で、見た目を上げる。何を上げるか（光・素材・家具の細部・外構など）は利用者と決める。

## 段階5: 三人称視点のウォークスルー
- **完成までは、URL の隠しスイッチの裏で開発する。** 本番に出しても、利用者の画面には出ない。
- **今の一人称のウォークスルーは1点も変えない。** 壁の当たり判定も今のまま。
- **5-1. カメラ**
  - 壁の向こうに出ない。壁が近いときは人物に寄る。
  - 上下のドラッグの向きは一人称と同じにする。
- **5-2. 人物と歩く動き**
  - 人物の出どころは要相談。
    - Codex に Blender で作ってもらう
    - 外部の素材を使う（利用条件と出典を台帳で確認してから）
- **5-3. 家具の動作（座るなど）**
  - 対象の家具に近づくと、何ができるかが分かる表示を出す。
- **5-4.** 0-2 の基準で負荷を確かめ、目標を満たしたら隠しスイッチを外す。外す前に、利用者に画面を見てもらう。

## 決まったこと（2026-10-07 利用者回答）

1. **段階の順序:** この文書の通り（0 → 1 → 2 → 3 → 4 → 5。3 は 0 のあと並行）
2. **0-2 の下限端末:** iPad Pro 第2・第3世代
3. **0-3 の AI 利用:** 基本は使ってよい。jev と残高を共有しているので、**残りが約500円を切ったら、実行前に止めて知らせる**。正解付きの図面は、手持ちの図面から作る
4. **1-2:** 「事件跡」「探索小物」は、TRPG 等の舞台作りで使えるものなので**残す**
5. **1-1・1-3:** 一括差し替えは「今のプランに適用し、Undo で戻す」。それとは別に、**洋館のモデルをサイドバーのカタログに出し、普通の日本の住宅にも1点ずつ置ける**ようにする。
   - そのため 1-1 の切り替えは「標準を隠して洋館だけにする」ではなく、「表示するセットを選ぶ（標準・洋館を同時に表示できる）」形にする
6. **4-3 の表現力:** 3D の画づくりのこと。写真のようなウォークスルーが理想。AA（輪郭のギザギザを消す）・DoF（被写界深度、ピントの前後をぼかす）・Bloom（明るい所がにじむ光）・AO（物の隅や接地に落ちる陰）などの描画手法を、iPad Pro 第2・第3世代で動く範囲から順に入れる。
   - 入れる順と効果は、段階4の詳細計画で、同じ視点の比較画像を並べて決める
7. **5-2 と制作の分担**
   - Codex: 家具・家財の Blender モデルと、画像（テクスチャ・プレビュー等）の制作
   - Claude: Meshy 等でのモデル生成、Mixamo でのモーションの取得と当てはめ、人物のモデル
   - 外部の素材は仮素材まで。本採用は独自制作
