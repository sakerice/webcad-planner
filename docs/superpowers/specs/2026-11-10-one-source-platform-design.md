## 1. 何のためにやるか

house-planner mobile（https://cad-planner.srapps.us）を、次の3つの形で出す。

1. Web 版（今のもの）。無料で、広告を出す。
2. ネイティブアプリ（iOS・Android）。サブスクを買うと、AI の機能を月ごとの回数の枠で使える。**2026-11-20 に変更:** サブスク（課金）はいったん範囲から外し、アプリも広告で無料にする（利用者決定 2026-11-20。7章）。
3. ChatGPT のアプリ。利用者自身の ChatGPT の契約で AI が動き、こちらは間取りを操作する窓口だけを提供する。

3つを別々に作ると、間取りの扱いが3通りに分かれて直すたびに食い違う。そこで、**間取りを操作する処理を1か所に集め、3つの出口がそれを共有する**。

同時に、大きな機能として「チャットで AI に間取りを作ってもらう・家財を足してもらう」を入れる。手順は利用者と合意済みで、次の2段で考える。

- 一歩め: 図面の画像があれば、既存の読み取り（`/api/ai/read-plan` → `review-plan-3d`）で間取りを起こす。
- 二歩め以降: 開いているプランに対して「洗面所を広く」「寝室にベッドを2つ」と言葉で頼むと、AI がプランへの変更を返し、画面に反映する。家財の追加もここに入る。

図面の無い人向けの「白紙から一括で作る」は、二歩めの仕組みの上に後から足す（合意済みの順番）。2026-11-20 に、これを試験する段に進めると決めた（利用者決定 2026-11-20。7章・9章）。

## 2. 目標・やらないこと・失敗とみなすこと

### 目標

- 間取りを変える操作（部屋の追加・寸法変更・壁・建具・家財の配置・移動・削除・設定変更・検査）を、画面に依存しない関数として1か所にまとめる。Web 画面、Worker のチャット、ChatGPT 向けの窓口が同じ関数を呼ぶ。
- チャットで頼んだ変更が、1回の取り消し（undo）で丸ごと戻せる。
- ネイティブアプリは Web と同じソース（`index.html` と `assets/`）を Capacitor で包んで作る。
- AI の利用回数は、アプリでは利用者ごとに srapps-billing の枠で数え、全体の財布の上限は今の `AiQuota` で守り続ける。（2026-11-20 に変更: 課金を外したので、srapps-billing の枠で数える部分は保留。全体の上限は `AiQuota` のまま守り、運営者の Anthropic API の費用を月 $100 以内に収める。3.5）
- リポジトリの一度きりの作業跡と配信物に混じった不要ファイルを片付け、テストが漏れなく走る状態にする。

### やらないこと（今回の範囲外）

- `index.html` 全体のモジュール分割やバンドラの導入。切り出すのは間取りの操作に関わる部分だけ（利用者決定: 段階的に進める）。
  **2026-11-20 に変更:** 公開物の整理（`index.html` の分割と、公開物に残る開発用の記述の片付け）は「取り組む」に変えた（利用者決定 2026-11-20）。外から見える物が雑だと、安全面の不安に加えて、いたずらの標的になりやすいため。段取りは調査中（9章）。
- 3D 描画（`buildWall3D` など）の作り直し。
- Web での販売（Stripe）。課金基盤の決定どおり、Web では買えない。
- 「白紙から一括で作る」専用の画面。チャットの延長で扱う。（2026-11-20 に、白紙からの間取りづくりを試験すると決めた。専用の画面を作るかは試験の結果で決める。7章）
- 男性の人物モデルなど、既存の持ち越し項目。

### 失敗とみなすこと（動いても駄目なもの）

- **既存利用者の保存プランが開けなくなる・見た目が変わる。** 互換の黄金テスト（`tools/tests/plan-compat.browser.mjs`）が1件でも変わったら止める。
- AI の答えを、決まりで勝手に書き換えて「直したこと」にする。合意済みの方針どおり、機械で分かる事実は AI に伝えて直させる。
- AI の費用が利用者の数に比例して青天井になる。全体の上限が働かない経路を作らない。
- API キーや秘密値がブラウザ・アプリ・ログ・リポジトリに出る。
- 画面に開発の都合（費用・トークン・秒数・座標）を出す。

## 3. 全体の構成

```
            ┌──────────── 同じソース（index.html + assets/）────────────┐
            │  Web 版（広告あり）          ネイティブアプリ（Capacitor）   │
            │        チャット欄 ─┐               チャット欄 ─┐              │
            └────────────────────┼───────────────────────────┼──────────────┘
                                 ▼                           ▼
   ChatGPT ──MCP──▶  Cloudflare Worker（今の worker.mjs に足す）
                      ├ /api/ai/chat        … Claude に道具付きで頼む（SSE）
                      ├ /api/mcp            … ChatGPT アプリの窓口（段5で /mcp から変更）
                      ├ /api/ai/read-plan 等 … 既存の読み取り
                      ├ /api/rooms/*        … 既存の共有ルーム（Durable Object + R2）
                      └ srapps-billing（Service Binding）… 権利と回数の枠（2026-11-20 から保留）
                                 │
                                 ▼
                 間取りの操作部品 plan-core（UMD、ブラウザ・Worker・Node で共通）
```

### 3.1 間取りの操作部品（plan-core）

置き場所は `assets/js/plan-core/`。形式は既存の手本（`plan-check.js`、`plan-free-apply.js`）と同じ UMD にする。ブラウザは `<script>` で、Worker は `import X from "../assets/js/plan-core/x.js"` で、テストは `require` で読む。

中身は次の5つ。それぞれ1本の PR で切り出し、前の段が本番に出てから次へ進む（3.6 の順番）。

1. **読み込みの正規化** `normalizeLoadedPlan(plan, ctx)`
   今は同じ手順が7か所（`loadPlanFromStorage`、`doImport`、`applySharedPatch`、`plan-library.js` の `loadIntoEditor`、`compare-mode.js`、`plan-import.js`、`plan-data.js` の `loadPreset`）に書かれ、中身が少しずつ違う。1つにまとめる。グローバルの `DATA` ではなく引数の `plan` を直し、`WALL_H` などのグローバルへの写しは呼ぶ側に残す。
2. **物を作る関数** `makeWall` / `makeItem` / `makeRoom`
   今の `mkWall` / `mkItem` を、id の発行とカタログ（`ISIZES`、manifest の寸法）を `ctx` で受け取る形にする。`index.html` 側の `mkWall` / `mkItem` は、これを呼ぶ薄い包みとして残す。
3. **差分の適用** `applyPatch`
   `worker/shared.mjs` の `applyPatch` と `index.html` の `applySharedPatch` を1つにする。共有する欄の範囲が今は両者で違うので、どちらに揃えるかは切り出しの PR で決めて説明に書く。
4. **操作（コマンド）** `applyOperations(plan, ops, ctx) → { plan, changedIds, warnings, errors }`
   1つの操作は `{ op: "addRoom", args: {...} }` の形。最初に用意する操作は次のとおり。
   - `addRoom` / `resizeRoom` / `renameRoom`（部屋）
   - `addWall` / `removeWall`
   - `placeItem`（家財・建具・設備。カタログの種類名で指定する）
   - `moveObject` / `rotateObject` / `deleteObjects`
   - `setProps`（設定できる項目は `assets/js/plan-settable.js` の `SETTINGS` を正本として使う）
   - （2026-11-21 に足した）`addRoomWalls` / `placeOpening` / `addRoof`（白紙から作る）
   - （2026-11-26 に足した）`swapAssetSet`（家具の一括差し替え）・`setAppearance`（壁紙・外壁・屋根のカラー設定）・`applyBuildingStyle`（建物の様式）。下の「AI の操作の追加（2026-11-26）」
   吸着（扉窓を壁へ、階段、格子）は `DATA` でなく引数の `plan` を見るように直して、操作の中で使う。操作が失敗したら、その操作だけを `errors` に入れて残りは続けず、**プランは変えずに返す**（全部か無しか）。
   画面側の `placeItem` / `delSel` / `updateSelectedProp` は「`saveState` → 操作 → 描画」の薄い包みに変える。undo は今の JSON スナップショット方式のままにする。
5. **検査** `inspectPlan(plan)`
   `PlanSchema.validatePlan`、`PlanCheck.knowledgeWarnings`、`PlanStructure.floorsOverlap` を束ねる。チャットと ChatGPT の「検査」道具に使う。`tools/lint_plan.py` の項目を移すのは今回はしない。

座標と単位は今の保存形のまま（mm、+x 東、+y 南、物の `x,y` は回転前の外接矩形の北西角）。ただし AI に渡す操作の引数は、読み取りと同じく**中心座標**で受け、操作の中で角に直す（読み取りの `toAppObjects` と同じ約束）。

### 3.2 操作の定義を1か所に置く

操作ごとに「名前・説明・引数の JSON Schema」を `assets/js/plan-core/operations-catalog.js` に1回だけ書く。ここから次の2つを生成する。

- Worker のチャットで Claude に渡す道具（tool）の定義
- ChatGPT アプリの MCP の道具の定義

引数の選択肢（家財の種類、設定項目）は `plan-settable.js` と `object-knowledge.js` から作り、手で書かない（読み取りの `plan-free.mjs` と同じやり方）。読み取りで、enum や anyOf が多いと Claude に「文法が大きすぎる」と断られた経験があるので、家財の種類は enum にせず文字列で受け、操作の中で照合して、合わなければ候補を `errors` に入れて返す。

### 3.3 チャット（Web とネイティブアプリ共通）

**前提: Worker は当面 Cloudflare の無料プランで動かす**（利用者決定）。無料プランは1リクエストの計算時間が 10ms まで（2026-10-29 更新の公式の上限表で確認）。そのため、Worker の中で Claude と何往復もしたり、プラン全体（約 93KB）を毎回読んで操作を当てたりはしない。**往復を回すのはブラウザ、Worker は鍵を持って1往復ずつ取り次ぐだけ**にする。今の読み取り（`worker/anthropic.mjs`）が「Worker では返事を読み解かない」作りにしているのと同じ考え方。

- 画面: 右下（スマホでは下）にチャット欄を開くボタンを置く。チャット欄の中で、画像を添付すると一歩めの読み取りに、文章だけなら二歩めの変更に進む。読み取りは既存の `runPlanImport` をそのまま呼び、チャット欄には進み具合だけを出す。
- 1回の依頼の流れ:
  1. ブラウザが `POST /api/ai/chat` に、会話の履歴・プランの要約（部屋・寸法・家財の一覧。プラン全体は送らない）・選択中の物の id を送る。
  2. Worker は回数を数え（3.5）、Claude に 3.2 の道具の定義を付けて1回だけ呼び、返事をそのまま SSE で流す（読み解かない）。
  3. ブラウザが返事の中の道具の呼び出しを読み、plan-core の `applyOperations` を**作業用の写し**に当てる。結果（変わった物・警告・失敗）を道具の結果として履歴に足し、もう一度 `/api/ai/chat` を呼ぶ。
  4. Claude が道具を呼ばずに返事を終えたら、写しを本物のプランに入れる。直前に `saveState` を1回だけ呼ぶので、1回の依頼が1回の undo で丸ごと戻る。
- 回数の数え方: 1回の依頼の最初の呼び出しで回数を1つ使い、Worker は署名つきの「依頼の札」を返す。同じ依頼の2回め以降はこの札を付けて呼び、回数を数えない。札には往復の上限（仮に 8 回）と有効期限を入れ、Worker が確かめる（既存の `plan-result` の受付番号と同じ HMAC 署名のやり方）。
- 費用: 道具の定義とプランの要約は毎回同じなので、Claude のプロンプトキャッシュを使う。
- 見直し: 読み取りで効いた「AI 自身に3Dで見直させる」は、チャットでは最初は入れない。変更が小さく、利用者がその場で見て次の依頼で直せるため。必要になったら `PlanSnapshot.capture` を使う形で後から足す。

### 3.4 ChatGPT アプリ（MCP）

- 同じ Worker に `/mcp`（Streamable HTTP）を足す。（段5で住所は `/api/mcp` にした。段5の結果を参照）MCP の道具は 3.2 の操作に、次の4つを加えたもの。
  - `create_plan`（空のプランで共有ルームを作る）
  - `open_plan`（共有ルームの URL を受け取り、そのプランを対象にする）
  - `get_plan`（プランの要約を返す）
  - `inspect_plan`
- 既存のプランを ChatGPT で直せるようにする（利用者決定）。画面に「ChatGPT で開く」ボタンを置き（段5で、ChatGPT に限らない「AIアプリで開く」として共有のダイアログに置いた）、押すと今のプランで共有ルームを作り、ChatGPT に貼る文（ルームの URL 入り）をコピーする。
- 無料プランの 10ms の中で、ルームのプランに操作を当てて保存できるかは**まだ確かめていない**。段5の最初に、実物大のプラン（既定プラン約 93KB）で計る。収まらなければ、プランの読み書きを階ごとの単位に分けるなどの作りに変える。Durable Object も無料プランでは SQLite 方式しか使えないので、`CollaborationRoom` がそれで動いていることも合わせて確かめる。
- プランの置き場所は、既存の共有ルーム（`CollaborationRoom`、Durable Object + R2）を使う。ChatGPT の会話ごとに1つのルームを作り、道具を呼ぶたびにルームのプランへ操作を当てて保存する。共有ルームの WebSocket がそのまま働くので、利用者が house-planner の画面で同じルームを開いていれば、変更がその場で映る。
- 利用者に返すもの: 変更の要約と、「house-planner で開く」リンク（ルームの URL）。ChatGPT の画面の中に間取りの絵を出す部品（Apps SDK の画面部品）は、2段めで入れる。
- 公開の範囲: まず ChatGPT の開発者モードで、利用者自身が使えるところまで（利用者決定）。公開ディレクトリへの申請は、srapps-billing 側で進むプライバシーポリシーの整備に合わせて行う。（2026-11-20: プライバシーポリシー・外部送信の公表などは、別のセッションで並行して進める。7章）
- 認証: 最初は認証なし。ルームの id（推測できない長さ）を知っていることを権限とする。課金も広告も付けない。ただし ChatGPT 経由で Worker が AI を呼ぶことは無いので、こちらの AI 費用はかからない。ルームの作成には接続元ごとの回数制限を付ける。
- 図面の読み取り（画像）は ChatGPT アプリでは提供しない。読み取りはこちらの Claude を使うため費用がかかるから。

### 3.5 ネイティブアプリ・課金・広告

**2026-11-20 に変更（利用者決定 2026-11-20）。** この節のうち課金（サブスク・srapps-billing の枠）に関わる部分は**保留**にした。理由は2つある。Claude や GPT が API の無料枠を用意するようになったこと、ネイティブで提供するための事業の届出がまだ済んでいないこと。まず Web とネイティブアプリの両方を広告で無料にして出す。広告と AI の費用については、次の 3.5.1・3.5.2 が今の方針で、その下の元の記述は経緯として残す。

#### 3.5.1 広告（2026-11-20 の方針）

- 広告の会社は、利用者の別のサービス「かさねて」に合わせる。Web は A8.net、iOS は AdMob。元の記述にある Google AdSense は取り消し。
- ネイティブアプリでも広告を出す。元の記述の「アプリの中（WebView）では広告を読み込まない」は取り消し。
- 枠の考え方は2種類。多くの場面に出すバナーと、利用者にとって良いことが済んで気持ちに余裕がある時（保存した後など）に出すインタースティシャル。作図中の画面を邪魔しない考え方は元の記述から引き継ぐ。
- 位置と頻度は 2026-11-21〜22 に利用者が決めた。実装は PR #138（2026-11-22 に main へ）。
  - **Web の常に出すバナーは画面の上端。** スマートフォンの横向き（高さ 500px 以下）では出さない。2D でも 3D でも同じ位置。帯の高さは CSS 変数 `--ad-h` で画面に伝え、アプリ全体をその分だけ下げる。
  - 素材の選び方は、幅に入るいちばん広い物（728×90、468×60、320×50）。**高さ 800px 未満の画面では高さ 60px 以下の物だけ**（468×60、無ければ 320×50。どちらも無ければ出さない）。小さいパソコン画面で図の広さが 16% 減るのを避けるため。
  - 画面の中の枠は、保存一覧・共有（300×250）と書き出し（320×50）に1つずつ。
  - すべての枠に「PR」と表記する。リンク先は `https://px.a8.net`、画像は `https://*.a8.net` だけを受け付ける。画像が読めないときは枠ごと消す。
  - 素材は `assets/js/pr-ads.js` の `PR_ADS` に足す。**0件のあいだは何も出ず、画面は変わらない。** 出し分けの判定は `adsMode()`（`'web'`・`'app'`・`'off'`）。元の記述の `shouldShowAds()` はこれに置き換えた。アプリの中では Web 用の A8.net の枠を出さない。
  - **外の AI が返したリンクで開いた画面には広告を出さない（利用者決定 2026-11-25、実装 2026-11-26）。** OpenAI と Anthropic のディレクトリの決まり（広告を出す物を載せない）と、利用者の体験のため。`adsMode()` はこの画面で `'off'` を返す。見分け方は2つを重ねた。
    - リンクの印。MCP の受け口（`worker/mcp.mjs` の `roomUrl`）が返すリンクを `…/#room=<id>&via=ai` の形にした。印は目印だけで、個人の情報は入らない。印があっても画面も MCP もルームの id を今までどおり読める。
    - ブラウザの覚え書き。印の付いたリンクで開いたルームの id を localStorage（`webcad-ai-rooms`、200 件まで）に残す。印の無いリンクで開き直しても、保存一覧から開き直しても、覚えているルームでは出さない。
    - 共有のダイアログの URL にも印を残す（`sharedRoomHash`）ので、リンクを渡された相手の画面でも出ない。一度この画面だと分かったら、ページを読み直すまで広告を戻さない（途中で帯が出て画面がずれないように）。
    - 印を消し、覚え書きも無いブラウザで開けば広告は出る。不正への備えはしていない。
    - 選ばなかった案は、ルーム側（Durable Object の meta）に「AI が作った」を持たせる案。どのブラウザでも外れない代わりに、ルームの中身を取り終えるまで広告を出すかどうかが決まらない。上端の帯は最初の絵の前に高さを空けているので、ふつうの共同編集のリンクで開いた画面の広告が遅れるか、AI のリンクの画面で一度 A8.net へ読みに行ってから消すことになる。
    - 決めていないこと: 利用者が自分で作ったルームを「AIアプリから直す」で外の AI に渡したとき、開いたままの画面の広告は今までどおり出る（AI が返したリンクから開き直した画面では出ない）。AI の変更が届いた時点で消すかどうかは未決。
  - **全面広告（インタースティシャル）は iOS アプリだけ。** 出すのは手で保存した直後と書き出しを終えた時。条件は、前の全面広告から保存2回以上かつ3分以上（「かさねて」と同じ）、1回の起動で1回まで、1日3回まで、初めて使った日は出さない。実装はネイティブの殻の段で行う。
  - Web の全面広告は作らない。A8.net の素材で出してよいかを A8.net に確かめていないため。
  - 広告を実際に出すのは、プライバシーポリシーと外部送信の公表がそろってから（法務・ストアの事務）。A8.net へのサイト登録と広告主との提携、AdMob へのアプリ登録は利用者が行う。

### AI の操作の追加（2026-11-26）

利用者に「AI から一括差し替えが使えない。家具の配置しかできないのか」と言われ、画面でできる見た目の変更を AI（チャット・MCP）からも使えるようにした。今の AI の操作は 16 個（`operations-catalog.js` の `OPERATIONS`）。

- `swapAssetSet {set, ids?, except?}`: 置いてある家具を別のセット（`rpg-mansion` 洋館・`kominka` 日本古民家）の物へまとめて差し替える。決め方は画面の「一括差し替え」と同じ `asset-swap.js` の `plan`、書き込みは同じ `applyRows`（画面の `apply` もこれを呼ぶ）。画面と違うのは、ロックした物を替えないことと、`ids`・`except` で替える物を選べること。選ばなかった物は替えず、載っている台が替わるときだけ高さを合わせる。選んだ台の替え先に含まれる上の物（洗面ボウルなど）は一緒に外し、その物がロック・`except` なら台ごと残す。Worker は `assets/data/worker-furniture.json`（`tools/build_worker_catalog.cjs` が画面の関数を呼んで作る）から引く。壁や天井に付けた物を壁掛け・天井吊りの物に替えるときに天井の高さが要り、勾配天井・吹き抜け・段差・天井の範囲・斜線制限のある部屋では Worker は断る（照明を置くときと同じ線）。
- `setAppearance {part, floor?, color?, texture?, sheen?}`: 内観（壁紙）・外観（外壁）・屋根のカラー設定の、家全体か階ごとの色・素材・屋根の質感。書き込みの決まりは `PlanCoreOperations.writeAppearance` で、設定欄（`updateInteriorSetting`・`updateExteriorSetting`・`updateRoofAppearance`）も同じ関数を呼ぶ。外観は設定欄と同じく「家全体」「階」の印を付けてから書く。素材と質感の一覧は `PlanSettable.APPEARANCE_TEXTURES`・`ROOF_SHEEN_OPTIONS`（設定欄もここを読む）。
- `applyBuildingStyle {set, parts?}`: 画面の「建物の仕上げを替える」と同じ。決め方は `BuildingStyle.planFor`、書き込みは画面の `apply` と共有にした `BuildingStyle.applyPlan`。ロックした部屋・扉・窓と、ロックした壁の面は変えない。Worker では、内観面・外観面の鍵と外壁のある階を 3D の壁の幾何から求められないので、理由つきで断る（幾何の要らない部位だけを当てることもしない。画面の結果と食い違うため）。
- `setProps` の `set` に、編集だけの項目（`editOnly`）を足した: 部屋の `floorColor`・`ceilingColor`、窓の `sashColor`、開き戸・折戸の `doorFinish`、部位を持つカタログの家具の `finishColors`・`finishTextures`・`finishRoughness`（`{部位: 値}`、今の値に重ね、`""` でその部位を既定に戻す）。読み取りの指示文（`describe`）と取り込みには出ない。

### 利用者が決めたこと（2026-11-20）
