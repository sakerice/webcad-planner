# house-planner mobile — 動画生成AI向け素材生成エンジン 設計

作成: 2026-08-07
関連: [映像生成エンジン 設計](2026-08-03-pv-render-engine-design.md)（PV制作用の内部ツール）

---

## 1. これは何か

**ユーザーが設計した家について、「実際に建った後の生活」を動画で見られる状態にする機能。**

本体はすでに **AIレンダー**（静止画）を持っている。3Dビューの構図を決めて実行すると、
base_render / edge / depth / normal / segmentation / instance の各ガイドと2つの legend、
そしてプロンプトを1つのパッケージとして書き出し、ユーザーが画像生成AIへ渡す。
本機能はその**動画版**であり、UIの形も出力の形も AIレンダーの延長線上に置く。

同じエンジンを、我々自身がPVを作るときにも使う。PV専用の作り込みは
[映像生成エンジン](2026-08-03-pv-render-engine-design.md) 側に置き、
本エンジンは「素材とプロンプトを作る」ところまでを担う。

### 1.1 なぜ別の資料にするか

PV側の設計は「shot spec を書いて連番フレームを撮り、動画を参照として渡す」ことを前提に
組んである。しかし実測の結果、**カメラが動く動画を参照にすると、生成側は構図が変わった
先で追従をやめて即興を始める**ことが繰り返し確認された（§9.1）。
ユーザー機能として出すなら、**構図を動かさない**ところから始める必要がある。
前提が違うので、資料を分ける。

---

## 2. 目的

1. ユーザーが、自分の設計した家の**生活シーンの動画**を、外部の動画生成AIで得られる。
2. その動画で、**間取り・建具・開口は設計どおりであること**が保たれる。
3. 光・素材の質感・空気感・人の営みは、生成AIに作らせる。三次元の真実は本体が決め、
   見た目の豊かさは生成AIが足す、という役割分担を崩さない。
4. 同じ出力で、我々がPVを作れる。

## 3. 非目標

- 動画生成を本体内で行うこと。生成は外部サービス（Seedance 等）で、ユーザーが実行する。
- 動画の編集・連結。複数カットを1本にまとめるのは編集の仕事であって、本機能の仕事ではない。
- 初版でカメラを動かすこと。§9 に拡張の道筋だけ置く。
- 斜線制限そのものの実装。§12.2 は勾配天井のデータの置き場所までを決める。

---

## 4. ユーザー体験

```
3Dビュー（または2D平面図）で構図を決める
        ↓
[🎬 動画AIレンダー] を押す
        ↓
表現プリセットを選ぶ（プロンプト入力欄に自動で入る／その場で書き換え可）
        ↓
生成 → ZIP をダウンロード
        ↓
Seedance 等へ、同梱の参照画像とプロンプトを渡す
```

既存の AIレンダー と同じ導線・同じダイアログ構成に寄せる。ユーザーから見て
「静止画で出すか、動画で出すか」の違いでしかない状態にする。

### 4.1 撮影対象を平面図にも広げる

現在の AIレンダー は常に3Dビューを撮る。ここに **2D平面図** を加える。

平面図を参照にすると「図面が家になる」という強い表現が作れる（§8 のプリセット参照）。
そのためには、図面から**設計に属さない描画物**を除いて撮る必要がある：

- 除外: メモ、寸法線（ruler）、選択ハイライト、グリッド、スナップ補助線、
  カスタムブロックの注記、UIオーバーレイ
- 残す: 壁、建具、部屋、階段、家具、什器、方位

この「注記抜きの平面図キャプチャ」は**既存の静止画AIレンダーにも同じものを提供する**。
片方だけに入れる理由がない。

## 5. 出力パッケージ

ZIP 1つ。中身は3種類。

### 5.1 静止画素材（AIが解釈するための絵）

| ファイル | 役割 |
|---|---|
| `reference.png` | **参照の本体**。ユーザーが決めた構図の、光と素材が乗った状態のレンダ |
| `edge_guide.png` | 構造の輪郭。壁・開口・屋根の稜線 |
| `depth_guide.png` | カメラ空間の深度。奥行き関係 |
| `normal_guide.png` | 面の向き。壁面・屋根勾配・ファサードの向き |
| `segmentation_guide.png` | カテゴリ別マスク |
| `instance_guide.png` | 部材個体別マスク |

生成AIに実際に投げるのは `reference.png` のみで足りることが多い。残りは
**プロンプトが部材を名指しするための根拠**であり、かつ我々の判定器（§10）が
使う。ZIPに入れるのは、ユーザーが別のツールで ControlNet 的に使う余地を残すため。

### 5.2 構造を把握できる図面

`plan_context.png` — 撮影した構図に対応するフロアの平面図（注記抜き）。
そこに**カメラの位置と画角を三角形で重ねる**。

これは生成AIへの入力としても効くが、それ以上に**ユーザーが「今どこを撮っているか」を
確認できる**ことが大きい。PV制作でも、カットの位置関係を人間が把握するのに要る。

### 5.3 プロンプト

`prompt.txt`。§7 の構造で組み立てる。ユーザーがダイアログで編集した内容がそのまま入る。

### 5.4 機械可読メタデータ

`package.json` — カメラ（位置・注視点・fov・視点高さ）、時刻/季節プリセット、
フロア、`instance-legend.json` / `segmentation-legend.json`、そして
**§6 の固定カテゴリ表**。判定器と、将来の再現に要る。

## 6. 固定の設計 — 何をどこまで動かしてよいか

本機能の核心。ユーザーの言葉を仕様にすると：

> 建具は強く固定し、家具はソフトに固定する。人が生活している場面や光の当たり方、
> 空気感のブラッシュアップは動画生成AIに任せる。

これを3階層で定義する。カテゴリは `instance-legend.json` の `type` から機械的に決まる。

### 6.1 LOCKED — 変えてはならない

**対象**: 壁、開口（窓・ドア・引戸・折戸）、階段、屋根、バルコニー、床・天井の範囲、
建物シルエット、敷地境界、造作収納、キッチン/水回りの躯体側

**根拠**: 設計そのもの。位置・寸法・数が変われば、それは別の家。

**プロンプトでの表現**: 個数と位置を**具体的に名指しする**。「変えるな」ではなく
「ここに何がある」を述べる。禁止の羅列は逆効果である（§9.2）。

> The room has three windows on the north wall and a single sliding door on the east.
> The stair rises along the west wall. Keep every opening where it is; add none.

### 6.2 SOFT — 存在と位置は保つが、見え方は変わってよい

**対象**: 家具、什器、家電、照明器具、植栽、カーテン

**変わってよいこと**: 素材の質感、布のしわ、反射、経年、色の深まり、
そこに置かれた小物、椅子が引かれている、といった**生活の痕跡**

**変わってはならないこと**: 個数、おおよその位置、種別（ソファがベッドにならない）

**プロンプトでの表現**:

> The seating, table and cabinets stay where they are and stay what they are.
> Let them gain real material — grain, weave, the creases of use.

### 6.3 FREE — 生成AIに作らせる

**対象**: 光の質、影の柔らかさ、空気感、天候、時間帯の情感、**人**、車、
窓外の景色、埃、反射、被写界深度

**制約**: 建築的な嘘は不可。**窓の無い壁から光を入れてはならない。**
人は建築を隠してはならない。人体スケールは 1.6–1.75m。

### 6.4 カテゴリ表は出力に含める

`package.json` に、各 instance がどの階層かを機械可読で入れる。
判定器（§10）はこれを読んで、階層ごとに違う厳しさで測る。

## 7. プロンプトの組み立て方

**構成比を守ることが仕様の一部である。** 実測（§9.2）で、禁止条項が本文の大半を
占めるプロンプトは生成をまるごと無効化することが分かっている。

```
1. 何を作るか（表現の指定）          ── 本文の 60〜70%
2. この家に何があるか（LOCKED の名指し） ── 20〜30%
3. 何をしてはならないか               ── 最後の 2〜3文まで
```

3 に書いてよいのは、**破ると設計が別物になること**だけ：

- 壁・開口・階段・家具を足すな、消すな、動かすな
- 線画・図面・フラットな未着色レンダに戻すな

**書いてはならないこと**: 個々の仕上げの色を「そのままにしろ」と命じること。
これは効かないうえ、生成そのものを止める（§9.3）。仕上げの保持は
**プロンプトではなく素材の側で担保する**（§8.3）。

## 8. 表現プリセット

選ぶとプロンプト入力欄に**自動で入り、ユーザーがその場で書き換えられる**。
プリセットは出発点であって、固定値ではない。

| プリセット | 入力になる素材 | 表現 |
|---|---|---|
| CAD図面 → 生活 | 平面図 | 図面が、上から見た実際の部屋へ変わっていく |
| CAD図面 → 生活（水彩風） | 平面図 | 図面に水彩がにじみ、生活の絵になる |
| 3D画面 → 生活 | 3Dビュー | 素材と光が乗り、写真になる |
| 3D画面 → 生活（水彩風） | 3Dビュー | 建築水彩パースへ変わる |
| 生活映像 | 3Dビュー | 最初から写実。人が動き、光が回る |
| 生活映像（水彩風） | 3Dビュー | 最初から水彩。人の気配がある |

### 8.1 「図面 → 生活」は入力が図面のときだけ許す

実測での失敗（§9.4）: 3Dレンダを参照にして「フラットな未着色CAD状態から始めて」と
書いたところ、生成AIは**渡した映像を捨てて線画を描き直した**。

入力が本当に平面図なら、その変換は正当で、しかも生成AIが得意とする。
入力が3Dレンダなら、その指示は破壊的。**プリセットは撮影した素材の種類に応じて
出し分ける。** 3Dビューを撮ったときに「CAD図面 → 生活」は選べない。

### 8.2 水彩系プリセットの注意

水彩は「素材の質感を曖昧にしてよい」という指示に近い。LOCKED の輪郭が緩む方向に
働くので、水彩プリセットでは §7 の 2（LOCKED の名指し）を厚くする。

### 8.3 仕上げは「言う」のではなく「見せる」

実測（§9.3）: 生成AIが仕上げをドリフトさせるかどうかを最も強く予測するのは、
**元のレンダでその部材がどれだけ暗いか**（Pearson −0.81）。
輝度30以下に潰れた部材は中央値43.7ドリフトし、それ以外は7.4だった。
ある部材の真の色は `#010302` — **モデルに何も見せずに「保て」と言っていた**。

したがって本エンジンは、`reference.png` を書き出す前に**暗部の露出を確認し、
潰れている部材があれば持ち上げる**。これはプロンプトでは代替できない。

## 9. なぜ静止参照から始めるのか

### 9.1 構図が動くと、見えていなかった部分で構造が壊れる

参照映像でカメラが動くと、生成AIは**元の映像に写っていなかった面を自分で作る**。
実測: 供給したフッテージの尺を超えた15秒版で、黒い革のアームチェアが出現し、
楕円テーブルが差し替わり、7.5秒でソファがほぼ消えた。

**構図を動かさなければ、見えていない面は最後まで見えない。** 構造が壊れる余地が
原理的に無くなる。初版はここから始める。

### 9.2 禁止条項が主体のプロンプトは、生成を素通しにする

実測: 本文の約8割が禁止条項だったプロンプトは、参照映像のほぼコピーを返した。
表現の指示を先頭に置き、拘束を末尾の一文に圧縮したところ、変換が始まった。

### 9.3 仕上げのドリフトは素材側の問題

§8.3 に記載。

### 9.4 「フラットなCAD状態から始めて」は3Dレンダを破壊する

§8.1 に記載。

### 9.5 参照に静止した区間があると、そこで追従が切れる

実測: 3カットを繋いだ12秒の参照動画のうち、末尾5秒が完全な静止画だった
（フレーム間差分が20サンプルすべて0）。生成AIはその区間で追従をやめ、
自前の記憶で描いた。**静止画1枚を参照にするのと、動画の中に静止区間があるのは、
生成AIにとって全く違う。** 前者は「これを保て」、後者は「ここから先は自由」と読まれる。

## 10. 検証

[映像生成エンジン](2026-08-03-pv-render-engine-design.md) の Layer 3（fidelity-qa）を
そのまま使う。本エンジンが `package.json` に §6 のカテゴリ表を入れるので、判定器は
階層ごとに違う閾値を当てられる。

| 指標 | LOCKED | SOFT | FREE |
|---|---|---|---|
| 輪郭の再現（消えていないか） | 厳格 | 緩い | 対象外 |
| 輪郭の発明（増えていないか） | 厳格 | 緩い | 対象外 |
| 部材ごとの仕上げ変化 | 厳格 | 緩い | 対象外 |
| 個数 | 完全一致 | 完全一致 | 対象外 |

ユーザー向け機能としては、判定器を**そのまま見せない**。
「間取りは保たれています / 一部の建具が変化しています」程度の要約に落とす。

## 11. 実装方針

- 既存の `generateAiRenderPackage()` と **ガイド生成経路を共有する**。
  動画版のために別のキャプチャ経路を作らない。二重化は必ず片方が腐る。
- 平面図キャプチャは新規。既存の 2D 描画（`draw2d`）に「注記を描かないモード」を足す形で、
  描画関数を分岐させるのではなく**描画対象のフィルタで実現する**。
- プリセットは1箇所のテーブルに置き、UIとプロンプト生成の両方がそこを読む。
- 破壊的変更は行わない。既存の AIレンダー の出力は1バイトも変えない
  （平面図キャプチャの追加は、既存のユーザーが使わなければ何も変わらない）。

## 12. 決定事項

### 12.1 暗部の持ち上げは書き出し時に行う

本体の3Dビューの見た目は出荷済みの製品であり、変えない。持ち上げは
**`reference.png` を書き出す経路だけ**に入れる。

手順:

1. `instance_guide.png` のマスクで、LOCKED / SOFT の各部材の平均輝度を測る
2. 輝度 30/255 を下回る部材が1つでもあれば、シャドウを持ち上げるトーンカーブを適用する
   （ハイライトはクリップさせない）
3. 適用したカーブを `package.json` に記録する

3が要るのは、**判定器が比較すべき相手が「モデルが実際に見た絵」だから**である。
持ち上げ前の生レンダと生成結果を比べると、我々が加えた補正がそのままドリフトとして
計上される。比較対象は書き出した `reference.png` とする。

### 12.2 平面図に高さ情報を持たせる

「平面図には高さ情報が無い」を、ガイドで補うのではなく**平面図の側を拡張して**解く。
これは本エンジンのためだけでなく、勾配天井・斜線制限といった今後の設計機能の土台になる。

現状の本体は高さを2つの定数で持っている（`index.html`）:

| 定数 | 現在値 | 意味 |
|---|---|---|
| `FLOOR_H` | 2700mm | 階高 |
| `WALL_H` | 2400mm | 壁高＝実質の天井高 |
| `FLOOR_SLAB_H` | 180mm | 床スラブ厚 |

つまり全室が一律 2400mm であり、部屋ごとの天井高も、下がり天井も、勾配天井も表現できない。

**追加するデータ（すべて省略可、省略時は現在の挙動と1ビットも変わらない）:**

```
floor.storyHeight      階高。既定 2700
room.ceilingHeight     天井高。既定 2400
room.ceiling = {
  type: 'flat' | 'sloped',
  //  sloped のとき
  lowMm, highMm,       低い側・高い側の天井高
  direction            勾配の向き（方位角、度）
}
```

**既定値は日本の注文住宅の一般的な寸法に合わせる:**

| 部位 | 既定 | 備考 |
|---|---|---|
| 階高 | 2700mm | 現行値。2900〜3000mm も一般的で、選択肢として出す |
| 居室の天井高 | 2400mm | 現行値。2500mm も一般的 |
| 水回り・廊下 | 2200mm | 下げるのが通例 |
| 下がり天井（梁下・設備）| 2100mm | 建築基準法の居室下限が 2100mm |
| ロフト | 1400mm 以下 | 階として算入されない上限 |
| 1F 床高（GL+） | 400mm | 基礎立ち上がり。現行の `foundationHeightM()` に対応 |
| 勾配天井 | 低 2200 / 高 3600mm | 斜線制限のかかる敷地で最も出番が多い形 |

**斜線制限との関係**: 道路斜線・北側斜線・隣地斜線は「この高さより上は建てられない」
という**面**を与える。勾配天井はその面に沿って屋根と天井を落とすことで生まれる。
つまり斜線制限の実装と勾配天井の実装は同じ幾何を共有する。ここでは
`room.ceiling.sloped` というデータの置き場所だけ先に決めておき、斜線制限そのものは
別の設計とする。

**平面図キャプチャへの反映**: 注記を落とした平面図に、**天井高だけは残す**。
部屋名の脇に `CH 2400` のように小さく置く。これは「注記」ではなく設計情報であり、
生成AIが空間の高さを推し量る唯一の手がかりになる。勾配天井の部屋では
`CH 2200-3600 ↗` のように向きも添える。

### 12.3 ZIPの既定は絞る

既定で入れるのは 4つ: `reference.png` / `plan_context.png` / `prompt.txt` / `package.json`。
6枚のガイドは「詳細ガイドを含める」チェックボックス（**既定オフ**）で追加する。

根拠: 実際に生成AIへ貼るのは参照画像とプロンプトだけである。ガイドは
プロンプトが部材を名指しするための根拠と、判定器の入力として使うものであって、
ユーザーが毎回持ち歩くものではない。

### 12.4 プロンプトはモデル非依存で書く

本文はモデルによらず共通とし、**末尾の付記だけ**をモデル別に差し替える
（参照の記法、尺・アスペクトの制約）。

根拠: MiniMax H3 が Seedance より仕上げを保つように見えた差は、実測で
**画面全体のカラーグレードを取り除くと消えた**（部材単位の優劣が 34/35 から
15/35 へ、p=1.0）。本文を書き分けるだけの根拠が無い。

### 12.5 尺は最大15秒

多くの動画生成AIの上限が15秒であり、それに合わせる。既定は **8秒**。

15秒は「1つの構図で持たせられる長さ」としても妥当で、§9.1 の破綻は構図を
固定している限り起きない。カットを重ねたい場合は複数回生成して編集で繋ぐ
（連結は本機能の仕事ではない、§3）。
