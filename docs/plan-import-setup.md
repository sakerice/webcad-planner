# 間取り図の読み取り — 設定と運用

間取り図のPDF・画像を読んで、壁・部屋・開口・階段を起こす機能。

## 何を使っているか

| 役目 | モデル | 1回の費用 |
|---|---|---|
| 図面の読み取り | **OpenAI `gpt-6-astra`** | 約 ¥40 / 図面1枚 |
| 読み取った結果の見直し | **OpenAI `gpt-6-astra`** | 約 ¥25 / 図面1枚 |
| 紙面のどこに平面図があるか | Google Vertex AI `gemini-2.5-flash`（東京） | 約 ¥0.2 / 1ページ |

3ページのPDFを1回取り込むと **約 ¥200**（実測 ¥197、141秒）。

### 自分の答えを見直させる

読み取りは、以前は投げて一度答えを受け取るだけだった。モデルは**自分の書いた
座標が間取りとしてどう見えるかを一度も見ていなかった**。

いまは、答えを画面側で平面図として描き直し（`assets/js/plan-review-draw.js`）、
元の図面と並べてもう一度渡して直させる（`POST /api/ai/revise-plan`）。
描くのは**モデルが答えたものそのもの**——部屋の長方形と、置いた物と、答えた
間口・奥行き——であって、アプリが後から組み立てた壁ではない。

何を直すかはこちらで列挙していない。決め打ちの検査項目を並べると、挙げた
項目しか見なくなる。渡すのは見比べる2枚と、直した結果を返す形だけ。

**上積みであって、必須の工程ではない。** 絵が描けない・通信に失敗する・上限に
達したときは、見直す前の結果をそのまま使う。ここで落ちて読み取り自体を失う
ほうが損になる。

直した内容は画面に出る（「2階の奥行きを 4170 → 4095mm に直しました」など）。
**黙って直すと、直ったことも直し損ねたことも分からない。**

### なぜ Astra なのか

同じ切り出し画像・同じ指示文・同じ仕様書で測った（1階の図面1枚）。

| | 費用 | 所要 | L字の部屋 | 廻り階段 | 寸法線4辺 |
|---|---|---|---|---|---|
| gemini-2.5-pro | ¥16 | 79秒 | ✗ | ✗ | ✓ |
| gpt-5 | ¥26 | 140秒 | ✗ | ✗ | 右辺✗ |
| **gpt-6-astra** | ¥40 | 73秒 | **✓** | **✓** | **✓** |

L字の部屋と廻り階段は、他の2つでは手順を書き直しても出なかった。Astra は
洋室を長方形2つで表して元図と完全一致させ、廻り階段を直進部分に接して置いた。
思考トークンは gpt-5 の1/10（1,552 対 15,360）で、迷わずに答えている。

**位置探しは Gemini のまま。** 大きな領域を1つ答えるだけで、そこに ¥40 を払う
理由が無い。ただし**安ければどれでもよいわけではない**。実測（正解は縦
0.240〜0.600）:

  gemini-2.5-flash  0.240〜0.600  ほぼ一致       ¥0.2
  gpt-5.4-mini      0.184〜0.308  上端だけを切る  ¥0.1

外した範囲で切り出して送ると、読み取りが「図面が無い」と答えて何も返らない。

## 処理される場所

**位置探しは東京リージョン（`asia-northeast1`）。** 読み取りは OpenAI の
既定のリージョン。

間取り図の表題欄には施主名・敷地住所が入ることが多い。OpenAI は API の
データを既定で学習に使わず、保存は不正利用監視の最大30日のみ。日本国内で
処理する設定（データレジデンシー）も API にあるが、**営業窓口での資格確認と
追加の契約条項が要る**（2026年9月時点。未申請）。

Vertex 側は、グローバルの窓口へ流れても**エラーにならず、黙って国外で処理
される**。動いてしまうので気づけない。そのため

- 窓口の組み立ては `worker/vertex.mjs` の `endpointFor` 1か所だけ
- 東京・大阪以外は組み立て自体を拒む
- 設定が国外なら**送信前に 500 で止める**
- `tools/tests/vertex-region.test.cjs` で固定

`asia-northeast3` はソウル。名前が似ているので取り違えに注意。

## 設定

### 鍵（本番）

    wrangler secret put OPENAI_API_KEY
    wrangler secret put GOOGLE_SERVICE_ACCOUNT_JSON

**鍵を置かないと機能は動かない。** OpenAI の鍵が無ければ Gemini で動くが、
L字の部屋も廻り階段も出ない。

ローカルは `.dev.vars`（gitignore 済み）に同じ名前で書く。

### 使用回数の上限

`/api/ai/*` には認証が無い。URLを知っていれば誰でも呼べ、そのまま請求される。

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `AI_MONTHLY_BUDGET_USD` | 80 | 月の金額の枠（米ドル。日本時間の暦月）。**財布の砦** |
| `AI_DAILY_BUDGET_MAX_USD` | 8 | 1日の額の上限の天井 |
| `AI_DAILY_BUDGET_MIN_USD` | 4 | 1日の額の上限の下限（月の残りは超えない） |
| `AI_DAILY_IMPORTS_PER_USER` | （未設定なら 168点 ≒ 2.7回） | 1つの接続元が1日に使える回数（1回 = 63点） |
| `AI_DAILY_IMPORTS_TOTAL` | （未設定なら 700点 ≒ 11回） | 全体が1日に使える回数（1回 = 63点） |
| `AI_CHAT_POINTS` | 21 | チャット1依頼の点 |
| `AI_CHAT_MAX_OUTPUT_TOKENS` | 24000 | チャット1依頼（往復をまたぐ）の出力の合計 |
| `AI_JEV_DAILY_PER_USER` / `AI_JEV_DAILY_TOTAL` | 30 / 300 | jev を呼ぶ窓口（仕上げ）の1日の回数 |
| `AI_RENDER_DAILY_PER_USER` / `AI_RENDER_DAILY_TOTAL` | 5 / 30 | アプリ内の AIレンダー（`/api/ai/render`）の1日の枚数。読み取りの点とは別に数え、金額の枠は共有する。**どちらかを `0` にするとレンダーだけを止める**（画面は「AIレンダーはいま使えません」と出して主ボタンを閉じる。読み取り・jev は止まらない）。未設定・空・数でない値は既定のまま |
| `AI_RENDER_MODEL` | gemini-nano-banana-2.1 | AIレンダーの画像モデル（Vertex AI、場所 global。鍵は読み取りと同じ `GOOGLE_SERVICE_ACCOUNT_JSON`） |
| `AI_RENDER_REPORTS_PER_USER` / `AI_RENDER_REPORTS_TOTAL` | 10 / 500 | AIレンダーの「問題を報告」の1日の件数。報告は R2 `PLANS` の `render-reports/<日本時間の日付>/` に入る |

**月の金額の枠**（2026-11 に足した。worker/ai-budget.mjs・worker/ai-price.mjs）。AI を呼ぶ前に、
その呼び出しの最悪額（入力の見積もり＋出力の上限×単価）を仮押さえし、枠を超えるなら呼ばずに断る。
返事の usage から実額を出して精算する。仮押さえは1回分で、単価は頼んだモデルと切り替わりうる先（claude-opus-5・
claude-opus-4-8）の高い方。途中で断られて別のモデルでやり直し、2回分課金されたときは、精算で usage どおりの実額を
足す（仮押さえを超えた分ではみ出すのは同時に走っている要求の分だけで、月の枠 $80 と $100 の間の余裕で受ける）。
- 上流が 2xx 以外を返したときは 0 で精算する（生成が始まっていないので課金されない、という前提）。
- 答えが途中で切れたとき（利用者が閉じた・流れが途切れた）は、入力は message_start の実数（取れなければ見積もり）、
  出力は `min(出力の上限, 経過秒数 × 300 + 1,000)` で精算する。Opus の生成の速さの3倍以上の余裕を見た上限で、
  厳密な保証ではない（漏れは月の枠 $80 と $100 の間の余裕で受ける）。
- 見積もりで精算した額と、精算されないまま期限の過ぎた仮押さえは、その人（IPv4 は1アドレス、IPv6 は /64）の
  「精算されずに残った額」に積む。1日の額の上限の 1/3 を超えると、その人だけ断る。
- 1人の1日の使用額（これまでに精算した額）が1日の額の上限の 1/3 を超えると、その人だけ「本日ぶん」で断る。
  仮押さえの大きさでは断らない（大きな1回は通し、次から断る）。
1日の額の上限は `min(月の残り, max($4, min($8, 2 × その日の始まりの月の残り ÷ 月の残り日数)))`。
OpenAI・Vertex に流れた分も、表のいちばん高い単価で同じ枠に数える。数える仕組みが返らないときは、どの入口も
AI を呼ばずに断る。大きな依頼だけが枠に入らないときは「混み合っています」と出し、いちばん小さな依頼も入らない
ときだけ「今月ぶん」「本日ぶん」と出す。上流のエラーの文は画面へ返さず、Workers のログ（`ai_upstream_error`）に出す。

運営者が今月の使用額を見るには、Workers のログで `ai_usage` を探す（日本時間の朝9時を過ぎた最初の AI の
呼び出しで、前の日と今月の額を1行出す）。外から金額が見える窓口は作っていない。

点（1日の回数）は、呼び出しによって費用が10倍以上違うため「点」で数えている
（1回 = 63点 = 3ページ×（位置探し1 + 読み取り10 + 見直し10））。

数える相手は接続元のIPアドレス。利用者の口座の仕組みがまだ無いため。
定額サブスクと使用回数制限を入れるときは、ここを口座ごとに替える。

画面には「本日あと N 回 読み取れます」を出す。**全体の上限があるので、自分が
使っていなくても使えないことがある。** 押してから断られるより、押す前に
分かっているほうがよい。ただし金額の枠で先に止まりうるときは、数を出さない（嘘になるため）。

### 支払い

OpenAI は**先払いのクレジット**。残高が $0 になると API が止まる。
自動チャージは OFF にしてある（想定外の使われ方をしたときに止まるほうが安全）。
残高は https://platform.openai.com/settings/organization/billing/overview で見る。

### 切り替え

| 環境変数 | 既定 | 意味 |
|---|---|---|
| `AI_IMPORT_PROVIDER` | （鍵があれば openai） | `vertex` にすると Gemini で読む。`gemini` にすると Gemini API で読む（`AI_GEMINI_FALLBACK=on` も要る。鍵の確かめ用） |
| `OPENAI_MODEL` | `gpt-6-astra` | 読み取りのモデル |
| `AI_LOCATE_PROVIDER` | vertex | 位置探しの提供元 |
| `AI_LOCATE_MODEL` | `gemini-2.5-flash` | 位置探しのモデル |
| `AI_FALLBACK` | （切り替える） | `off` にすると、提供元が一時的に失敗しても別の提供元へ切り替えない |
| `AI_GEMINI_FALLBACK` | （使わない） | `on` のときだけ、予備の3番目に Gemini API（秘密 `GEMINI_API_KEY`）を使う |
| `GEMINI_MODEL` | `gemini-4-hydrogen` | 予備の Gemini のモデル |

提供元が一時的に失敗したとき（通信の失敗・429・5xx・529・401・403）は、次の提供元へ1回ずつ切り替える
（worker/ai-fallback.mjs）。読み取りと見直しの順番は Claude → OpenAI → Gemini で、鍵の無い提供元は飛ばす。
画面の読み取り（read-plan）で Claude が失敗したら、画面はこれまでの読み取り（import-plan）へ移り、そこでは Claude を
もう一度呼ばずに OpenAI から始める。位置探しは Vertex → OpenAI。
`AI_IMPORT_PROVIDER`・`AI_LOCATE_PROVIDER` で名指ししているときは切り替えない。チャットと、組み立てた家の見直し（review-plan-3d）は切り替えない。

Gemini API は既定では使わない。無料の枠では、送った内容と答えが Google の製品の改善に使われ、人が読むことがある
（https://aistudio.google.com/docs/terms の Unpaid Services）。請求アカウントが有効な Cloud プロジェクトの鍵なら改善に使われない
（同 Paid Services）。鍵のプロジェクトが有料の段かは、Google AI Studio の Projects ページの Billing Tier の欄で見る
（https://aistudio.google.com/docs/billing）。有料（Tier 1 以上）を確かめてから `AI_GEMINI_FALLBACK=on` にする。
Gemini の分も月・1日・1人の額の枠に数える（単価は worker/ai-price.mjs の GEMINI_PRICES、有料の段の公表値）。

## 設定

### 1. Google Cloud 側（済み）

- プロジェクト `webcad-planner-ai`（この用途専用。請求と権限を分けるため）
- Vertex AI（Agent Platform API）を有効化
- サービスアカウント `plan-import@webcad-planner-ai.iam.gserviceaccount.com`
- 権限は Agent Platform ユーザー（このプロジェクト内のみ）

### 2. 手元で試すとき

```bash
export VERTEX_KEY_FILE=~/.config/webcad/vertex-key.json
node tools/probe_vertex.cjs <PDFか画像> [--model gemini-2.5-flash] [--out plan.json]
```

読み取れた部屋・使用トークン数・**1回あたりの費用**・検算の結果・
寸法がモジュールに乗っている割合が出る。`--out` で保存したJSONは
アプリの「読込」からそのまま開ける。生の応答も `.raw.txt` に残るので、
形が想定と違ったときに**もう一度お金を払わずに**調べられる。

### 3. 本番（Cloudflare Worker）

```bash
npx wrangler secret put GOOGLE_SERVICE_ACCOUNT_JSON
```

鍵ファイルの中身（JSON全体）をそのまま貼る。**鍵はここにしか置かない。**
ブラウザへは出さない（`tools/tests/vertex-region.test.cjs` が、応答にも
エラーにも鍵が出ないことを見ている）。

任意で変えられる設定:

| 環境変数 | 既定値 | |
|---|---|---|
| `VERTEX_LOCATION` | `asia-northeast1` | 東京・大阪以外は拒否される |
| `VERTEX_PLAN_MODEL` | `gemini-2.5-pro` | 費用を抑えるなら `gemini-2.5-flash` |
| `VERTEX_PROJECT` | 鍵の project_id | |

## 費用

3ページのPDF（3階建て全体）を、読み取り＋見直しで **1回 約 ¥197**
（実測 2026-09-19、gpt-6-astra、入力 52,790 / 出力 15,753 トークン、141秒）。

画面に出る金額は `assets/js/plan-import.js` が gpt-6-astra の単価
（$10 / $50 per 1M、$1=¥150）で計算している。**モデルを替えたらここも替える。**
実際より安く見えるのが一番まずい。

以下は Gemini で測っていた頃の記録。思考トークンの効き方は同じ。

**費用の8割以上は「思考」。** 答えのJSONは2,000〜4,800トークンで、思考が
8,000〜19,500トークン。だから

- 出力JSONを詰めても安くならない（試したところ逆に思考が84%増えた）
- **思考に上限を置く**のが効く（`thinkingBudget`、既定8192）
- 上限が無いと費用に上限が無い。実際、検算を促す指示を入れたら思考だけで
  32,765トークンを使い切り、答えが0トークンのまま打ち切られた

読み取り結果には使用トークン数が必ず付き、画面にも1回あたりの費用が出る。

## 精度を左右するもの

**解像度がすべて。** 寸法の文字が読めるかで結果が決まる。

- **PDFはそのまま送る。** ベクターなのでAI側で開いたほうが鮮明。実測で
  4辺の寸法線がすべて検算を通り、寸法の99/99件がモジュール上に乗った
- 画像は長辺2400pxまで送る（1568pxでは 7280 を 7290 と誤読した）
- 切り出し（囲む操作）は**任意**。紙面の一部にしか図面が無い画像でだけ効く

## 設計の勘どころ

**部屋はAIに出させない。** 壁と「図に書かれた室名とその位置」だけを出させ、
囲まれた領域は `assets/js/plan-rooms.js` が計算する。両方出させると食い違い、
同じ図面で部屋が3〜9個に変動した。壁から作れば必ず一致する。

**寸法の読み違いは機械的に直す。** 日本の住宅の寸法は 227.5mm（4分の1間）の
倍数に乗るので、50mm以内なら倍数へ寄せる（実測の誤読: 227.5→275、455→450、
7280→7290）。遠い値は触らない — 本当に半端な寸法のこともある。

## まだ足りていないところ

- 壁の読み取りに、実在しない間仕切りが混じることがある。**壁の精度が
  そのまま部屋の精度になる**構造なので、次に詰めるならここ
- 下の寸法線は読み違えることがある（補正で吸収しているが根治ではない）
- 写真（紙を撮影したもの）ではまだ試していない。PDFとCAD出力の画像のみ
